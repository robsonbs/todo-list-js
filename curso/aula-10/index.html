1 A ilha, o servidor e o backend

O navegador executa a interface. O backend é o programa que recebe pedidos, aplica regras e conversa com o banco. Node.js permite executar JavaScript fora do navegador; Express ajuda a organizar as rotas HTTP desse servidor.

O JavaScript sai do navegador?

No curso inicial, o JavaScript normalmente roda dentro do navegador e pode acessar a página por meio do DOM. O Node.js é outro lugar para executar JavaScript: nele não existe a página atual, mas há recursos para criar um servidor e conversar com outros programas.

Peça Onde roda Responsabilidade nesta aplicação
HTML/CSS/JS Navegador Mostra a lista e reage às ações da pessoa.
Node.js + Express Servidor Recebe HTTP, valida, autentica e decide operações.
PostgreSQL Servidor de dados Guarda contas, sessões e tarefas entre visitas.

Node.js, npm e Express não são a mesma coisa

  • Node.js executa JavaScript no servidor.
  • npm instala e organiza pacotes do projeto.
  • Express é um pacote que organiza rotas HTTP em Node.js.

Do terminal ao navegador

  1. O terminal inicia o processo Express com `npm run dev`.
  2. O processo fica aguardando pedidos na porta configurada (3000 por padrão).
  3. `localhost` significa “este mesmo computador”; não significa que o site já está público.
  4. Quando o terminal para o processo, o servidor local deixa de responder.
# Na pasta do projeto, usando Node.js 26.13.0
npm ci
docker compose --env-file .env.example -f docker-compose.web.yml --profile aplicacao up app-web

# Em outro terminal:
curl http://localhost:3000/api/health

A saída esperada do último comando é JSON com status igual a ok. Isso confirma que o processo responde; ainda não prova que cadastro, login ou banco estejam configurados para produção.

Desafio relâmpago: se fechar o navegador, qual parte continua disponível para atender outro aparelho? Resposta: o servidor e o banco, se estiverem publicados e funcionando.

2 HTTP: o correio da web

Uma requisição leva um pedido do cliente ao servidor; uma resposta informa o resultado. O método descreve a intenção: GET consulta, POST cria, PATCH altera parcialmente e DELETE remove. Cabeçalhos dão contexto, o corpo pode carregar JSON, e o status resume o resultado (por exemplo, 200, 201, 400, 401, 404 ou 500).

As peças de uma requisição

POST /api/tarefas?origem=lista HTTP/1.1
Host: localhost:3000
Content-Type: application/json
Accept: application/json
Cookie: tarefas.sid=...

{"texto":"Estudar HTTP"}
  1. POST é o método: a intenção é criar algo.
  2. /api/tarefas é o caminho do recurso; ?origem=lista é uma query opcional.
  3. Content-Type descreve o formato enviado; Accept indica o formato que o cliente espera receber.
  4. A linha vazia separa os cabeçalhos do corpo JSON.
  5. O cookie leva o identificador da sessão; o navegador não manda o ID do dono da tarefa.
Não confunda os lugares: o caminho responde “qual recurso?”, a query pode filtrar uma consulta, os cabeçalhos dão contexto e o corpo carrega dados da operação. Nenhum desses valores substitui a identidade que o servidor obteve da sessão.

As peças de uma resposta

HTTP/1.1 201 Created
Content-Type: application/json

{"tarefa":{"id":"...","texto":"Estudar HTTP","completa":false}}

O status 201 significa que algo foi criado. A resposta também tem cabeçalhos e, neste exemplo, um corpo JSON. Não confunda status com o texto que aparece na tela.

Método Intenção Exemplo nesta API
GET Ler sem alterar Listar tarefas próprias
POST Criar Adicionar uma tarefa
PATCH Alterar parte Editar texto ou conclusão
DELETE Remover Excluir uma tarefa própria

Como ler os códigos de status

O que `fetch` faz quando recebe um erro HTTP?

`fetch()` normalmente não rejeita a Promise só porque o servidor respondeu 400 ou 401. Ele entrega um objeto de resposta. A interface precisa conferir resposta.ok antes de tratar o JSON como sucesso. Falha de rede, por outro lado, cai no catch.

3 Express: organizar as entregas

Express é um pacote para Node.js que ajuda a montar um servidor HTTP. Uma rota combina método e caminho; um middleware é uma etapa reutilizável executada no caminho da requisição, como conferir uma sessão.

Primeiro: um servidor que responde

import express from 'express';

const app = express();

app.get('/api/health', (requisicao, resposta) => {
  resposta.status(200).json({ status: 'ok' });
});

app.listen(3000, () => {
  console.log('Servidor aguardando em http://localhost:3000');
});

app.get registra uma rota GET. Express chama a função quando chega um pedido para esse caminho. resposta escolhe o status e o corpo; app.listen começa a aguardar pedidos na porta 3000.

O que querem dizer com “API REST”?

REST é uma convenção para organizar uma API ao redor de recursos. Aqui o recurso é tarefas: o caminho nomeia o recurso e o método HTTP descreve a ação. REST não é outro servidor nem um pacote que Express instala.

Leia em voz alta: `PATCH /api/tarefas/42` significa “alterar parte da tarefa identificada por 42”. É o método/caminho, não o nome de uma função JavaScript, que define o contrato HTTP.

Middleware: a fila de conferências

app.use(express.json({ limit: '10kb' }));
app.use('/api/auth', rotasAutenticacao);
app.use('/api/tarefas', exigirAutenticacao, rotasTarefas);
app.use(tratarErros);

A ordem importa: express.json interpreta corpos JSON antes das rotas que leem requisicao.body. Depois podem entrar a conferência de sessão, a rota e o tratamento final de erros. Limitar o corpo reduz o espaço para pedidos enormes.

Origem Exemplo Leitura em Express
Parâmetro do caminho /api/tarefas/:id requisicao.params.id
Query string /api/tarefas?status=pendente requisicao.query.status
Corpo JSON {"texto":"Estudar"} requisicao.body.texto, após `express.json()`

O que significa `next`?

Um middleware chama next() para entregar o pedido ao próximo middleware. Se chama next(erro), Express pula as rotas comuns e procura o middleware de erro. No Express 5, rejeições de uma rota assíncrona também chegam ao tratamento central de erros.

Uma rota de leitura da lista

roteador.use(exigirAutenticacao);

roteador.get('/', async (requisicao, resposta) => {
  const resultado = await poolBanco.query(
    `SELECT id, texto, completa
     FROM tarefas
     WHERE usuario_id = $1`,
    [requisicao.usuario.id]
  );

  resposta.status(200).json({ tarefas: resultado.rows });
});

🔎 Leia a rota

roteador.get atende consultas GET. O middleware exigirAutenticacao roda antes. requisicao contém o pedido e resposta constrói a resposta. O valor $1 é enviado separado do SQL; seu ID vem da sessão, não de um campo escolhido pelo navegador.

4 Banco de dados: arquivo com regras

Um banco relacional organiza informações em tabelas. Colunas descrevem propriedades; linhas representam registros. Uma chave primária identifica cada registro. Uma chave estrangeira conecta registros relacionados e ajuda a manter os dados consistentes.

Pense em fichários, não em uma planilha sem regras

Uma tabela guarda um tipo de coisa. Uma linha é um registro; uma coluna descreve um campo. O banco também aplica regras para impedir valores inválidos. Por exemplo, e-mail não pode se repetir e tarefa precisa apontar para uma conta existente.

Versão pequena das tabelas que o projeto persiste
usuarios tarefas
id · email · hash_senha id · usuario_id · texto · completa
42 · ana@example.test · $argon2id$… 81 · 42 · Estudar HTTP · false
57 · bia@example.test · $argon2id$… 94 · 57 · Revisar SQL · true

Os IDs numéricos desta ilustração são encurtados para facilitar a leitura. No banco real do projeto, os identificadores são UUIDs.

  • Chave primária (PK): identifica uma linha sem depender do texto/e-mail da pessoa.
  • Chave estrangeira (FK): aponta para a chave primária de outra tabela; aqui, `tarefas.usuario_id`.
  • Restrição: regra do banco, como e-mail único ou texto não vazio.
Missão de modelagem: se Ana criar 100 tarefas, por que gravamos o e-mail uma vez em `usuarios` e ligamos as tarefas pelo `id`? Porque repetir dados cria divergências e dificulta mudanças.

5 PostgreSQL e SQL

PostgreSQL é o programa de banco de dados; SQL é a linguagem usada para pedir operações a ele. O driver `pg` faz a ponte entre Express e PostgreSQL. O pool reaproveita um conjunto limitado de conexões, em vez de abrir uma conexão nova para cada tarefa.

CRUD: quatro operações para trabalhar com registros

-- READ: listar tarefas de uma conta
SELECT id, texto, completa
FROM tarefas
WHERE usuario_id = $1
ORDER BY criada_em DESC;

-- CREATE: criar uma tarefa
INSERT INTO tarefas (usuario_id, texto)
VALUES ($1, $2)
RETURNING id, texto, completa;

-- UPDATE: alterar uma tarefa própria
UPDATE tarefas
SET completa = true, atualizada_em = now()
WHERE id = $1 AND usuario_id = $2;

-- DELETE: remover uma tarefa própria
DELETE FROM tarefas
WHERE id = $1 AND usuario_id = $2;

CRUD é uma sigla para Create, Read, Update, Delete: criar, ler, atualizar e remover. Repare que as consultas de alteração incluem o dono. Isso transforma uma regra do sistema em condição do banco, não apenas em um botão escondido.

Olhe o banco que está rodando

`psql` é um cliente de terminal para conversar com PostgreSQL. O comando `\dt` lista tabelas; ele é um comando do `psql`, não SQL. Dentro do laboratório local, podemos inspecionar as tabelas e depois consultar alguns registros fictícios. 

docker compose --env-file .env.example -f docker-compose.web.yml up -d banco-web
docker compose --env-file .env.example -f docker-compose.web.yml run --rm migrar
docker compose --env-file .env.example -f docker-compose.web.yml exec banco-web \
  psql -U todo_dev -d todo_web

-- No prompt do psql:
\dt
SELECT id, texto, completa FROM tarefas;

Um banco recém-iniciado pode não ter tarefas; o resultado vazio não é erro. Primeiro rode as migrações e crie uma conta pelo laboratório.

Por que `$1` e `$2`?

O driver recebe o texto SQL e os valores em argumentos separados: poolBanco.query(sql, [usuarioId]). Não concatene o texto digitado ao SQL. Parâmetros separam dados do comando e ajudam a prevenir SQL injection.

Desafio da bibliotecária: o navegador envia o texto da tarefa, mas de onde vem o usuario_id? Dica: o formulário não é uma fonte confiável; procure o valor na sessão que o servidor verificou.

6 API, persistência e migrações

Uma rota recebe o pedido e valida os dados. O pool entrega uma conexão ao driver pg; o PostgreSQL executa o SQL e devolve linhas. A rota transforma o resultado em status e JSON para o navegador. Nenhuma etapa deve confiar no dono informado pelo formulário.

Pool de conexões é um conjunto pequeno de conexões reaproveitáveis. Abrir uma conexão custa tempo e recursos; o pool empresta uma, deixa a rota consultar e depois a devolve.

Uma criação, do HTTP ao banco

  1. O navegador envia POST /api/tarefas e um corpo JSON.
  2. Express interpreta o JSON, valida texto e sessão e chama a rota.
  3. A rota usa o ID obtido da sessão e parâmetros SQL separados.
  4. PostgreSQL grava e devolve a nova linha; Express responde 201.
  5. A interface atualiza a tela somente após confirmar o sucesso.
const resultado = await poolBanco.query(
  `INSERT INTO tarefas (usuario_id, texto)
   VALUES ($1, $2)
   RETURNING id, texto, completa`,
  [requisicao.usuario.id, textoValidado]
);

resposta.status(201).json({ tarefa: resultado.rows[0] });

`resultado.rows` é uma lista de linhas devolvidas pelo driver. O parâmetro `$1` é o dono determinado pela sessão; `$2` é o texto que passou pela validação do servidor.

O que é uma migração?

Uma migração é um arquivo SQL versionado que descreve uma mudança planejada no esquema. O projeto registra o nome de cada migração em `schema_migrations` e não a reaplica quando já consta como concluída. Assim, um colega ou servidor novo chega à mesma estrutura do banco. 

npm run db:migrate

# No fluxo Docker local:
npm run db:migrate:docker

Quando várias alterações precisam ser atômicas

A importação de várias tarefas usa uma transação. BEGIN inicia o grupo, COMMIT confirma tudo, e ROLLBACK desfaz tudo se uma inserção falhar. A pessoa não fica com metade das tarefas importadas. 

const cliente = await poolBanco.connect();
try {
  await cliente.query('BEGIN');
  await cliente.query('INSERT INTO importacoes_locais (usuario_id) VALUES ($1)', [usuarioId]);
  await cliente.query('INSERT INTO tarefas (usuario_id, texto) VALUES ($1, $2)', [usuarioId, texto]);
  await cliente.query('COMMIT');
} catch (erro) {
  await cliente.query('ROLLBACK');
  throw erro;
} finally {
  cliente.release();
}

Todas as instruções da transação usam o mesmo `cliente`. O `finally` devolve essa conexão ao pool tanto no sucesso quanto no erro.

Por que criar um índice?

O índice `tarefas_usuario_criacao_idx` ajuda o banco a encontrar e ordenar tarefas de uma conta sem examinar todas as linhas. Índices aceleram consultas frequentes, mas ocupam espaço e também têm custo ao inserir; não crie um índice para cada coluna sem motivo.

7 Contas, senhas e sessões

Autenticação responde “quem entrou?”; autorização responde “o que essa pessoa pode acessar?”. São duas perguntas diferentes e o sistema precisa responder às duas.

Hash não é criptografia reversível

Na criptografia, quem possui a chave adequada pode recuperar o texto original. Um hash de senha é calculado num sentido: quando a pessoa entra, a biblioteca compara a senha informada com o hash salvo sem o sistema precisar guardar a senha original. O projeto usa Argon2id por meio de uma biblioteca mantida.

O que o navegador guarda após o login?

O servidor cria uma sessão e armazena nela o ID e o e-mail da conta. O navegador recebe um cookie com um identificador opaco e assinado; nas próximas requisições, o servidor usa esse identificador para encontrar a sessão. O cookie não contém a senha nem uma lista de tarefas. Depois do login, o ID de sessão é regenerado para reduzir ataques de fixação de sessão.

  1. Cadastro: o servidor normaliza o e-mail e armazena o hash Argon2id da senha.
  2. Confirmação: o servidor cria um token aleatório curto; no banco guarda apenas o hash e a expiração.
  3. Login: compara a senha com o hash e cria uma nova sessão server-side.
  4. Recuperação: um token de uso único troca a senha e revoga sessões antigas.

O cookie tem atributos diferentes com funções diferentes: HttpOnly impede o JavaScript de ler o cookie; Secure exige HTTPS em produção; SameSite restringe quando o navegador o envia em navegação iniciada por outro site. Nenhum deles substitui a autorização no backend.

Analogia: o cookie é o número do guarda-volumes; a sessão no servidor é o armário. Saber um número não autoriza a pessoa a abrir o armário de outra.

🗺️ Como interpretar o Mermaid

A pessoa só inicia a ação. O navegador envia cookie e token CSRF; o Express verifica a sessão e a requisição antes de gravar. O ID usado na consulta é derivado da sessão, o que impede que trocar um identificador na tela dê acesso às tarefas de outra pessoa.

Tokens de confirmação de e-mail e redefinição de senha são aleatórios, expiram e só podem ser usados uma vez. O banco guarda o hash do token, não o link que foi enviado.

8 Proteger a aplicação web

Segurança não é um botão do Express. Ela aparece em várias camadas: validar entrada, autenticar a sessão, autorizar a operação e limitar o que o servidor revela quando algo dá errado.

Risco Exemplo Defesa aplicada
SQL injection Texto digitado vira parte do comando SQL. Placeholders `$1`, `$2` e valores separados.
XSS Texto de tarefa é interpretado como HTML executável. Exibir com `textContent`, CSP e sem HTML do usuário.
CSRF Outro site tenta enviar uma ação usando os cookies da vítima. Token CSRF em cada alteração e cookie `SameSite`.
Acesso cruzado Ana troca o ID da URL para tentar abrir tarefa de Bruno. Consulta sempre combina `id` e usuário da sessão; resposta `404`.
Roubo de sessão Cookie de sessão viaja sem proteção. HTTPS e cookie `HttpOnly`, `Secure` e `SameSite`.

Por que `textContent`?

// Texto como dado: o navegador não o interpreta como HTML.
elemento.textContent = tarefa.texto;

// Não fazer: o texto do usuário pode ser interpretado como marcação.
// elemento.innerHTML = tarefa.texto;

Argon2id protege hashes de senha, mas não cifra uma senha para recuperá-la. CSRF protege ações, não substitui autenticação. HTTPS protege o tráfego, mas não corrige autorização fraca. Cada defesa tem uma função diferente.

Desafio A/B: Ana altera o ID na URL e tenta remover uma tarefa de Bruno. A interface até pode esconder o botão; que verificação impede a operação de verdade? Resposta: o backend inclui o usuário da sessão na condição do `DELETE`.

9 O navegador conversa com a API

O frontend usa fetch para enviar HTTP. Enquanto espera, mostra carregamento; depois verifica o status e só então atualiza a tela. Um status 400 ainda é uma resposta HTTP: por isso precisamos olhar resposta.ok. Uma falha de rede, como servidor desligado, cai no catch. 

const resposta = await fetch('/api/tarefas', {
  method: 'GET',
  headers: { Accept: 'application/json' },
  credentials: 'same-origin'
});

if (!resposta.ok) {
  throw new Error('Não foi possível carregar as tarefas.');
}

const dados = await resposta.json();

Criar exige método, cabeçalhos, corpo e CSRF

const resposta = await fetch('/api/tarefas', {
  method: 'POST',
  credentials: 'same-origin',
  headers: {
    'Content-Type': 'application/json',
    'X-CSRF-Token': tokenCsrf
  },
  body: JSON.stringify({ texto: 'Estudar Express' })
});

if (!resposta.ok) {
  const erro = await resposta.json();
  mostrarMensagem(erro.erro);
}
  1. JSON.stringify transforma o objeto JavaScript em texto JSON para o corpo HTTP.
  2. Content-Type informa ao Express como interpretar o corpo.
  3. credentials: 'same-origin' permite enviar cookies para a mesma origem.
  4. O token CSRF vem de GET /api/csrf-token e fica apenas na memória da página.
  5. Depois da resposta 201, a interface limpa o formulário e atualiza a lista.

Mesma origem e CORS

Origem é a combinação de protocolo, domínio e porta. Nesta edição, Express entrega a tela e `/api` no mesmo endereço, então o navegador não precisa liberar uma segunda origem por CORS. Se a tela e a API forem hospedadas em domínios diferentes, o servidor precisa permitir explicitamente a origem correta; liberar qualquer origem junto com cookies não é uma solução segura.

Decisão de migração: depois do login, a interface oferece importar as tarefas da chave local `tarefas`. A API valida cada item e registra que a conta importou; uma segunda tentativa retorna 409 Conflict em vez de duplicar dados.
Checkpoint: se `fetch` receber 401, explique por que isso não é a mesma coisa que o servidor estar offline.

10 Testar e preparar o lançamento

Testes diferentes respondem perguntas diferentes. Teste unitário confere uma regra pequena; integração confere HTTP mais banco; navegador E2E confere a jornada visível. Nenhum deles, sozinho, prova toda a segurança.

Tipo O que confere Comando
Unitário Regra pura de validação e estado npm test
Integração API, sessão, SQL e duas contas isoladas npm run test:integration:docker
E2E local Jornadas da versão original e imagens do curso npm run test:e2e
E2E web Telas públicas, erros e responsividade da edição online npm run test:e2e:web

Local não é produção

`localhost` só aponta para o próprio computador. Para publicar, o host precisa executar a imagem `Dockerfile.web`, conectar-se a um PostgreSQL alcançável e entregar domínio HTTPS. O provedor desta edição ainda precisa ser escolhido; a Vercel atual serve o site estático, não inicia sozinha este backend.

  1. Crie um banco de produção separado dos bancos de desenvolvimento e teste.
  2. Configure `DATABASE_URL`, `SESSION_SECRET`, `CSRF_SECRET`, `PUBLIC_URL` HTTPS e SMTP no gerenciador de segredos do host.
  3. Se houver proxy TLS, configure `TRUST_PROXY_HOPS` para o número real de proxies confiáveis.
  4. Execute migrações como etapa de release; não permita que qualquer réplica altere o esquema ao iniciar.
  5. Configure backups e ensaie a restauração. Um backup nunca foi testado até ser restaurado.

O `.env.example` contém valores locais e deliberadamente inseguros para produção. Não faça commit de `.env`, segredos SMTP ou URLs de produção.

Critério de sucesso: explicar o percurso navegador → HTTP → Express → PostgreSQL e concluir uma tarefa pela aplicação publicada.
